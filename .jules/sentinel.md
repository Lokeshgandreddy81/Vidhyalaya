## 2024-10-18 - [Node.js VM Sandbox Escape via Prototype Chain]
**Vulnerability:** A vulnerability was discovered in the `executeSanitizedUserCode` function inside `backend/src/utils/codeRunner.js`. The function used the native Node.js `vm` module (`vm.runInNewContext`) to sandbox and execute user code, providing an `executionContextSandbox` which contained standard JavaScript objects (e.g. `{ process: { env: { NODE_ENV: 'production' } } }`). This allowed malicious user code to exploit the prototype chain via standard objects and invoke the `Function` constructor from the host context (e.g. `process.env.constructor.constructor('return process')()`). As a result, users could execute arbitrary code within the host context, completely bypassing the sandbox restrictions and executing malicious commands or stealing secrets on the server. Furthermore, a host function was injected `process.exit = () => { throw new Error(...) }` which could also be used to traverse up to the host Function prototype.
**Learning:** Using standard JavaScript objects to construct a sandbox context for the Node.js `vm` module is highly dangerous. Standard objects inherit from `Object.prototype`, which in turn leads to the `Function` constructor. The `vm` module inherently does not provide full isolation from the host environment unless it is carefully configured. If any standard objects from the host context are passed to the VM context, they act as an escape hatch, allowing the sandboxed code to walk up the prototype chain, reach the host's global context, and execute code dynamically. Injecting host functions is equally dangerous as it exposes the host Function prototype.
**Prevention:**
1. Always create all objects passed to a VM context recursively using `Object.create(null)` to ensure they have no prototype chain.
2. Specifically use `vm.createContext` instead of `vm.runInNewContext` to configure strict code generation restrictions.
3. Configure the context with `codeGeneration: { strings: false, wasm: false }` to block the dynamic evaluation of code from strings, making the `Function` constructor unexploitable even if somehow accessed.
4. Avoid injecting host function references directly; rely on throwing or intercepting state if needed, or define the mock entirely within the sandboxed eval code block.
5. Execute the code with `vm.runInContext`.
