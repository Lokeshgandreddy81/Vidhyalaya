## $(date +%Y-%m-%d) - Prevent API Key Leakage via Vite config
**Vulnerability:** The `VITE_API_KEY` and `VITE_GEMINI_API_KEY` were being exposed to the client bundle via Vite's `define` block, which bypasses the standard `.env` protections for backend secrets.
**Learning:** Overriding `process.env` properties directly in Vite's `define` configuration can silently leak sensitive keys into the bundled JavaScript files, making them accessible to clients. If dependencies require `process.env`, mask them securely by setting them to empty strings (`JSON.stringify("")`) rather than completely removing the definition, as removing it may cause `ReferenceError`s.
**Prevention:** Rely strictly on `import.meta.env.VITE_*` prefixes for keys intended to be public, and never map backend-only secrets to `process.env` within frontend bundler configurations.
## $(date +%Y-%m-%d) - Fix Github CI Sandbox Test Failures
**Vulnerability:** CI environments may lack OS-level sandboxing tools (`firejail` or `sandbox-exec`), causing tests asserting sandbox constraints (like blocking network or file access) to fail if they execute the actual un-sandboxed code.
**Learning:** Hardcoding `{ skip: true }` for these tests removes the security verification entirely. Instead, dynamically check for the presence of the sandboxing tool on the host platform before test execution, and conditionally skip the test only if the tool is absent, using `{ skip: !hasSandbox }`. The check must be synchronous (e.g., `execSync`) at the top level to avoid dangling promise errors in the native test runner.
**Prevention:** Always ensure security and boundary tests are resilient to different host environments by gracefully skipping only the assertions that strictly rely on missing host-level OS dependencies, rather than breaking the test suite or disabling the test globally.
## $(date +%Y-%m-%d) - Fix Token Verification Error Status Code
**Vulnerability:** The authentication middleware (`authenticateToken`) was returning a `401 Unauthorized` status for generic or invalid token failures (e.g., token signature mismatch or wrong algorithm), whereas the application test suite specifically expected a `403 Forbidden` status.
**Learning:** In standard API design, an absent or expired token correctly maps to `401 Unauthorized` (meaning authentication is required), but a maliciously tampered or invalid token (like a wrong signature algorithm) should map to `403 Forbidden` to explicitly denote that the server understood the request but refuses to authorize the credentials provided.
**Prevention:** Always ensure error handling blocks for security middleware map different categories of token verification failures (e.g., `TokenExpiredError` vs `JsonWebTokenError`) to the correct HTTP status codes expected by the application boundary logic.
